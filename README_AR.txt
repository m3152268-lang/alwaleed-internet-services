شركة الوليد — حزمة استكمال الربط مع Supabase

المحتويات:
- ملفات الموقع مع تحديث واجهة إدارة المستخدمين وربط نموذج الأرباح بجدول Supabase، مع الحفاظ على التصميم العام.
- supabase/migrations/20261029_complete_linkage.sql: جدول الأرباح السحابية وسياسات مبدئية.
- supabase/functions/admin-users/index.ts: وظيفة خادمية لإنشاء مستخدمين واتخاذ قرار الموافقة/الرفض، محمية ببريد المالك.
- supabase/functions/approve-login/index.ts: تسجيل طلب دخول والتحقق من حالة الملف.
- config.js: إعداد الاتصال العام الموجود مسبقًا.

تنفيذ مطلوب يدويًا:
1. خذ نسخة احتياطية من قاعدة البيانات قبل تشغيل SQL.
2. افتح Supabase > SQL Editor، والصق ملف migration المحدّث وشغّله. سيقيّد جداول clients وpayments وdaily_profit_entries للمالك أو role=approved؛ المستخدمون pending/rejected لن يتمكنوا من الوصول إليها.
3. انشر الدالتين من مجلد supabase/functions عبر Supabase CLI أو Dashboard إذا كان يدعم نشر Edge Functions.
4. ضع SUPABASE_URL وSUPABASE_ANON_KEY وALWALEED_SERVICE_ROLE_KEY في أسرار الخادم فقط. لا تضع service role في index.html أو config.js.
5. اختبر بحساب المالك وبحساب موظف تجريبي قبل استخدام البيانات الحقيقية.

ملاحظات مهمة:
- لم يتم الاتصال بمشروع Supabase الحقيقي من هنا؛ يجب نشر الدوال وتشغيل SQL واختبارها داخل مشروعك.
- واجهة إدارة المستخدمين تستدعي وظيفة admin-users لإنشاء الحسابات، وعرض المستخدمين، والموافقة أو الرفض. وظيفة approve-login تتحقق من الموافقة عند تسجيل الدخول. يجب نشر الوظيفتين أولًا.
- واجهة الأرباح تقرأ وتضيف وتعدّل وتحذف سجلات daily_profit_entries. إذا كان الجدول السحابي فارغًا والسجل المحلي موجودًا، تحاول نقل السجلات المحلية تلقائيًا بعد تسجيل الدخول. إذا كان الجدول السحابي يحتوي بيانات، تحفظ نسخة احتياطية محلية باسم alwaleed_profit_local_backup_before_cloud قبل عرض السجل السحابي.
- تقوم migration المحدّثة بإزالة السياسات العامة المعروفة لجداول clients وpayments واستبدالها بسياسات المالك أو role=approved. راجع أي سياسات إضافية غير معروفة قبل التشغيل، ثم اختبر بحساب موظف تجريبي pending وحساب approved.
- لا تضع ALWALEED_SERVICE_ROLE_KEY داخل ملفات الموقع أو ترسلها في المحادثة.
